[정산자금 외부관리](/posts/2026-09-01-pg-settlement-fund-segregation)나 [클라우드 이용 신고](/posts/2026-07-28-pg-cloud-service-usage-reporting) 같은 개별 규제 대응은, 사실 하나의 공통 인프라 위에서만 지속 가능하다. 원장·정산 배치·리스크 엔진·감사로그, 이 네 컴포넌트를 처음부터 제대로 설계하지 않으면 규제가 바뀔 때마다 매번 땜질이 된다. 여기서는 "무엇을 만들어야 하는가"보다 "어떤 옵션 사이에서 무엇을 트레이드오프하는가"에 집중한다.

## 왜 이 네 개인가

PG/선불 사업의 규제 대응은 결국 세 가지 질문으로 수렴한다 — 돈이 누구 것인지 증명할 수 있는가(원장), 정산이 정확하고 재현 가능한가(정산 배치), 이상거래를 걸러낼 수 있는가(리스크 엔진), 누가 언제 무엇을 했는지 변조 불가능하게 남길 수 있는가(감사로그). 넷 중 하나라도 빠지면 나머지 셋이 아무리 잘 돼 있어도 감사·수사 대응에서 뚫린다.

## 아키텍처 옵션과 트레이드오프

**1. 원장 — 범용 RDBMS 직접 구현 vs 특화 원장 엔진**
double-entry(차변/대변) 원장을 자체 RDBMS 스키마로 구현하면 기존 클라우드 인프라(국내 리전 RDS Multi-AZ 등, [클라우드 이용 절차](/posts/2026-07-28-pg-cloud-service-usage-reporting) 참고)를 그대로 재사용할 수 있다는 장점이 있지만, 트랜잭션 동시성·원자성을 스키마 레벨에서 올바르게 짜는 게 생각보다 어렵다. 반대로 [TigerBeetle](https://github.com/tigerbeetle/tigerbeetle) 같은 결제 전용 원장 데이터베이스는 계정·이체를 1급 원시 타입으로 다뤄 동시성 문제를 엔진이 대신 해결해주지만, 자체 프로토콜을 새로 익혀야 하고 국내 리전에서 직접 운영·이중화까지 책임져야 한다(매니지드 서비스가 아직 제한적). [Formance Ledger](https://github.com/formancehq/ledger)는 PostgreSQL 위에서 동작해 기존 RDS 운영 노하우를 재사용할 수 있는 절충안이지만, 오케스트레이션 레이어까지 쓰면 벤더 종속이 커진다. [Midaz](https://github.com/LerianStudio/midaz)는 소스공개(Elastic License 2.0)라 완전한 오픈소스는 아니므로 라이선스 검토가 먼저다. 결제·정산 트랜잭션 처리량이 초당 수백 건을 넘어가는 규모가 아니라면, 특화 엔진 도입보다 기존 RDBMS 위에 double-entry 스키마를 제대로 짜는 쪽이 운영 부담이 오히려 작다.

**2. 정산 배치 — 셀프호스팅 오케스트레이터 vs 클라우드 매니지드**
Airflow류의 DAG 기반 오케스트레이터는 복잡한 배치 파이프라인의 가시성이 좋지만, 스케줄러 자체를 이중화·재해복구 대상으로 관리해야 한다는 부담이 있다 — [클라우드 이용 규정](/posts/2026-07-28-pg-cloud-service-usage-reporting)이 요구하는 이중화 요건이 배치 스케줄러 인프라 자체에도 그대로 적용된다는 뜻이다. AWS Step Functions/EventBridge Scheduler 같은 매니지드 옵션은 이중화 부담이 줄어드는 대신 벤더 종속이 커진다. 어느 쪽을 택하든 도구 선택보다 중요한 건 재실행 안전성이다 — 배치 ID + 상태 머신 기반으로 동일 배치가 재실행돼도 중복 지급이 없어야 하고, 부분 실패는 실패 건만 격리해 재처리해야 한다(전체 배치 재시작은 이중 지급 리스크).

**3. 리스크·사기탐지 엔진 — 자체 구현 vs 상용 SaaS**
상용 사기탐지 SaaS는 초기 구축 속도가 빠르고 최신 사기 패턴 반영이 상대적으로 빠르지만, 실시간 결제 데이터를 외부로 내보내야 하므로 그 벤더까지 클라우드 이용 신고·망분리 재평가 대상에 포함해야 한다 — 벤더 하나 붙일 때마다 컴플라이언스 검토 항목이 하나씩 늘어난다는 뜻이다. 자체 구현(규칙 기반 엔진 또는 Flink 등 스트림 처리 기반 이상탐지)은 데이터가 내부에 머물러 컴플라이언스 부담이 작지만, 사기 패턴 대응 속도는 전문 벤더보다 느릴 수밖에 없다. 초기 단계에는 자체 규칙 엔진으로 시작하고, 손실률이 특정 임계치를 넘어설 때 상용 SaaS 도입을 재검토하는 단계적 접근이 현실적이다.

**4. 감사로그 — 인프라 레벨 변조 방지가 애플리케이션 레벨보다 우선**
누가, 언제, 어떤 사유로 정산 계좌에 접근·이체했는지에 대한 불변 로그가 필요하다는 요구는 [정산자금 외부관리 글](/posts/2026-09-01-pg-settlement-fund-segregation)에서 이미 다뤘다. 선택지는 두 갈래다 — 로그 엔트리마다 이전 엔트리 해시를 포함하는 해시체이닝을 애플리케이션 레벨에서 자체 구현하거나, AWS CloudTrail + 별도 계정 S3 Object Lock(WORM) 같은 인프라 레벨 변조 방지를 쓰는 것. 감사 대응 관점에서는 후자가 유리하다 — "애플리케이션 코드가 정직하게 짜였다"를 증명하는 것보다 "인프라 자체가 수정을 물리적으로 거부한다"를 증명하는 게 감사인 입장에서 훨씬 검증하기 쉽다.

## 체크리스트

- [ ] 원장이 double-entry(차변/대변) 구조인지, 단일 잔액 컬럼으로 관리되고 있지 않은지
- [ ] 결제 처리량 기준으로 범용 RDBMS와 특화 원장 엔진 중 무엇이 맞는지 재검토했는지
- [ ] 정산 배치가 배치 ID + 상태 머신 기반으로 멱등하게 설계됐는지, 배치 스케줄러 자체의 이중화가 돼 있는지
- [ ] 리스크·사기탐지 데이터가 외부 벤더로 나간다면, 그 벤더까지 클라우드 이용 신고·망분리 대상에 포함했는지
- [ ] 감사로그가 애플리케이션 레벨이 아니라 인프라 레벨 변조 방지(Object Lock 등)를 갖췄는지
- [ ] 선불 사업을 겸업한다면 선불충전금(100% 이상 별도관리 의무)을 PG 정산자금과 원장에서 별도 계정과목으로 분리했는지, 발행잔액·연간 총발행액이 등록 면제 기준(각 30억원·500억원)을 넘는지 주기적으로 확인하는지
