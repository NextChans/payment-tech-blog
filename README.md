# 결제·핀테크 엔지니어링 브리핑

PG/간편결제/전자금융 규제 동향과, PG·선불 사업을 운영하는 데 필요한 인프라·시스템 구성을 엔지니어 관점에서 분석하는 SEO 블로그. Next.js 14 App Router + TypeScript + Tailwind, 콘텐츠는 `content/posts`의 마크다운 파일로 관리한다.

두 개의 콘텐츠 트랙을 운영한다:
- **규제·정책 트랙**: 전자금융거래법 등 규제 개정, 금융위/금감원 공시 — 그 주 실제 뉴스 기반
- **인프라·시스템 트랙**: AWS 인프라 설계, 클라우드 이용 신고 등 컴플라이언스, PG/선불 사업에 필요한 시스템 구성, 오픈소스·상용 툴 비교

매주 그 시점에 가장 시의성 있는 소재(규제 트랙 우선, 마땅한 소재가 없는 주는 인프라·시스템 트랙)를 골라 한 편을 발행한다.

## 로컬 실행

```bash
npm install
npm run dev       # http://localhost:3000
npm run build     # 프로덕션 빌드 검증
```

빌드는 이미 한 번 검증됨(타입체크 통과, 정적 페이지 생성 확인).

## 배포 (Vercel 기준, 5분)

1. 이 폴더를 GitHub 리포지토리로 push
2. [vercel.com](https://vercel.com)에서 New Project → 해당 리포 선택 → 기본 설정 그대로 Deploy
3. 커스텀 도메인 연결 후 `app/layout.tsx`, `app/sitemap.ts`, `app/robots.ts`의 `SITE_URL`을 실제 도메인으로 교체 후 재배포
4. Vercel은 무료 티어로 충분 (개인 블로그 트래픽 기준)

## 새 글 작성

```bash
npm run new-post -- "글 제목"
```

`content/posts/YYYY-MM-DD-slug.md`가 생성된다. frontmatter(title/description/date/tags/keywords/category)를 채우고 본문을 마크다운으로 작성하면 끝. `category`는 `"regulation"`(트랙 A, 규제·정책) 또는 `"infra"`(트랙 B, 인프라·시스템) 중 하나 — 홈페이지 카테고리 필터가 이 값을 기준으로 동작한다.

## 수익화 체크리스트

- **애드센스**: 글 10~15편, 각 1,000자 이상의 순수 오리지널 콘텐츠가 쌓인 뒤 신청하는 걸 권장 (콘텐츠 부족 상태에서 신청 시 반려 확률 높음). 승인 전까지 `components/AdSlot.tsx`가 자리만 잡아둠. 승인 후 해당 컴포넌트를 실제 `<ins class="adsbygoogle">` 태그로 교체.
- **제휴/스폰서**: PG사·핀테크 SaaS(정산 자동화 툴, 결제 모니터링 SaaS 등) 대상 스폰서 콘텐츠. 니치가 좁고 타겟(핀테크 개발자·PM)이 명확해서 애드센스보다 단가가 높을 가능성이 큼.
- **뉴스레터 전환**: 트래픽이 붙으면 이메일 수집 폼을 추가해 스티비 등으로 뉴스레터 병행 — 같은 콘텐츠를 재사용 가능.

## SEO 키워드 전략

"핀테크 뉴스" 같은 광범위 키워드는 경쟁이 세서 승산이 없다. 대신 실무자가 검색하는 롱테일 키워드를 노린다:

- "PG 정산자금 외부관리", "전자금융거래법 개정 PG업"
- "간편결제 수수료 공시", "PG사 수수료 비교 2026"
- "다단계 PG 구조 규제", "전자금융업 등록 요건"
- "PG 시스템 아키텍처", "정산 배치 멱등성"
- "전자금융업 클라우드 이용 신고", "PG AWS 인프라 설계"
- "PG 시스템 구성", "선불전자지급수단 시스템 아키텍처"
- "결제 시스템 오픈소스 툴", "PG 원장 시스템 상용 솔루션"
- "전자금융업자 경영지도기준", "전자금융업자 경영개선명령", "미상환잔액 자기자본비율"
- "금융복합기업집단 전자금융업자", "그룹 위험관리체계 PG", "통합자본적정성"

각 글의 frontmatter `keywords` 필드에 타겟 키워드를 채워두면 메타데이터에 반영된다.

## 콘텐츠 캘린더 (다음 후보)

### 트랙 A — 규제·정책 (그 주 실제 뉴스 기반, 우선순위 높음)

1. ✅ 정산자금 외부관리 의무화 — 개정 전금법과 PG 개발팀 대응 (발행됨)
2. ✅ 다단계 PG 규제, 10월 시행 하위 PG사 분기 평가 의무 (발행됨)
3. ✅ 결제수수료 공시 확대 — PG사는 공시 데이터를 어떻게 자동 생성할 것인가 (발행됨)
4. ✅ 경영지도기준 위반 전자금융업자 10곳 자본금 증액 명령(2026-07-31, 티메프 사태 이후 첫 건전성 조치) — 개발팀이 미상환잔액·자기자본을 상시 모니터링해야 하는 이유 (발행됨)
5. ✅ 전자금융업자도 금융복합기업집단 소속금융회사에 포함(2026-07-31 의결) — 대형 금융그룹 계열 PG·선불사가 그룹 위험관리체계에 뭘 준비해야 하는지 (발행됨)
6. 국내 PG사 수수료 구조 실측 비교 — 신용카드/간편결제/해외결제 기준

### 트랙 A 확장 — 전자금융업 등록 시리즈 (여러 편으로 나눠 진행, 한 번에 한 편만, category: "guide")

시의성 있는 새 뉴스가 없는 주에는, 위 트랙 A 후보보다 먼저 이 시리즈에서 아직 안 쓴 편을 하나 골라 쓴다. 뉴스 기반이 아니라 "그래서 어떻게 등록하는데" 하고 검색하는 사람을 겨냥한 평가 참고형 시리즈다 — 트랙 A(시의성 뉴스)와 검색 의도가 달라서 홈페이지 카테고리도 `regulation`이 아니라 별도의 `guide`를 쓴다. 회차별로 실제 조문·요건 수치는 작성 시점에 다시 확인한다(면제 기준 등은 이미 다른 글에서 다룬 수치와 어긋나지 않는지 확인).

- ✅ 등록1: 전자금융업이 뭔지, 우리 서비스가 등록 대상인지 아닌지부터 판단하는 법 (등록/신고/예외 구분) (발행됨)
- ✅ 등록2: PG업(전자지급결제대행업) 등록에 필요한 자본금·인력·전산설비 요건 (발행됨)
- ✅ 등록3: 선불전자지급수단발행업 등록에 필요한 요건과, 등록이 면제되는 소규모 기준 (발행됨)
- ✅ 등록4: 등록 신청부터 승인까지 실제 절차·필요 서류·심사 기간 (발행됨)
- 등록5: 등록만 하고 끝이 아니다 — 등록 후에도 계속 지켜야 하는 의무 요약과, 이 블로그의 다른 글(클라우드 이용 신고, 정산자금 외부관리 등)로 연결

### 트랙 B — 인프라·시스템 구성 (규제 트랙에 마땅한 소재가 없는 주에 사용)

5. ✅ 전자금융업자 클라우드 이용 신고·보고 의무 — AWS/GCP를 쓰는 PG·선불사가 놓치기 쉬운 것 (발행됨)
6. ✅ PG/선불 사업에 필요한 최소 시스템 구성 — 원장, 정산 배치, 리스크 엔진, 감사로그 아키텍처 (발행됨)
7. ✅ AWS 기반 결제 인프라 설계 — 가용성·이중화·재해복구(멀티 AZ/리전) 관점에서 결제 시스템이 요구하는 것 (발행됨)
8. 오픈소스 vs 상용 — 원장·정산·사기탐지 툴 비교와 PG 규모별 선택 기준
9. 결제 시스템 모니터링·관측성 스택 — 오픈소스(Prometheus/Grafana/OpenTelemetry) vs 상용 APM

매주 소재 선택 순서: ① 트랙 A(그 주 시의성 있는 규제 뉴스) → ② 없으면 전자금융업 등록 시리즈에서 아직 안 쓴 편 하나 → ③ 그것도 소진됐거나 안 맞으면 트랙 B. 트랙 B 글도 "일반론 설명"이 아니라 실제 AWS 서비스명·오픈소스 프로젝트명·최근 버전 등 구체적 근거를 갖춰 써야 한다 — 소재가 항상 구체적이어야 "양산형 AI 콘텐츠"로 분류되지 않는다. 트랙 A는 배경/규제내용/체크리스트/참고자료 구조를, 트랙 B와 등록 시리즈는 배경/핵심 내용(또는 아키텍처 옵션 비교·트레이드오프)/체크리스트/참고자료 구조를 따른다. 등록 시리즈는 한 번에 한 편만 쓴다 — 여러 편을 한 실행에서 몰아 쓰지 않는다.

## 자동 발행 파이프라인 (GitHub Actions)

`.github/workflows/weekly-post-draft.yml`이 매주 수요일 09:00 KST(UTC 00:00)에 실행되어 최신 뉴스를 리서치하고 초안을 작성한 뒤, **main에 직접 push하지 않고** `weekly-draft/YYYY-MM-DD` 브랜치로 PR을 연다. `npm run build` 검증을 통과하면 PR을 그대로 main에 머지까지 진행한다 (2026-09-02, 사용자 지침 — 이전에는 사람이 머지했으나 자동 머지로 정책 변경).

실제 작업 지침(콘텐츠 트랙, 리서치 기준, 작성 구조, 날짜 지정 규칙, SEO 체크리스트 등)은 워크플로우 파일이 아니라 `.claude/skills/weekly-blog-draft/SKILL.md`에 있다. 이 문서는 실행마다 갱신되도록 설계된 살아있는 매뉴얼이라, 워크플로우 프롬프트를 매번 고치는 대신 이 파일만 고치면 다음 실행에 반영된다.

### 최초 설정 (한 번만)

1. Claude GitHub App 설치: https://github.com/apps/claude → 이 저장소에 설치
2. 인증 방식 선택 (저장소 Settings → Secrets and variables → Actions):
   - **Pro/Max 구독이 있으면(권장, 별도 과금 없음)**: 로컬 터미널에서 `claude setup-token` 실행 → 나오는 토큰을 `CLAUDE_CODE_OAUTH_TOKEN` 시크릿으로 등록
   - 구독이 없으면: [console.anthropic.com](https://console.anthropic.com)에서 API 키 발급 → `ANTHROPIC_API_KEY` 시크릿으로 등록하고, 워크플로우 파일의 `claude_code_oauth_token` 줄을 `anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}`로 교체
3. Actions 탭 → "Weekly Fintech Blog Draft" → "Run workflow"로 한 번 수동 실행해서 정상 동작 확인

### 리뷰 워크플로우

빌드 검증을 통과한 PR은 자동으로 main에 머지되어 프로덕션에 배포된다. 필요하면 머지 후에도 Vercel 배포 로그·글 내용을 확인해 문제가 있으면 되돌리기(revert) 커밋으로 수정한다.

이 GitHub Actions 파이프라인이 유일한 자동화 경로다. (과거 Cowork에 동일 역할의 주간 스케줄 작업이 별도로 있었으나 중복 방지를 위해 중지했다.)

## 왜 이 구조인가 (설계 노트)

- MDX 대신 순수 마크다운 + `gray-matter` + `remark-html`: 의존성 최소화, 빌드 안정성 우선
- 각 포스트는 로컬 markdown 파일 — CMS 없이 git 커밋만으로 발행 이력 관리됨
- `AdSlot` 컴포넌트는 애드센스 승인 전/후 전환이 컴포넌트 교체 한 줄로 끝나도록 분리해둠
