# 주간 블로그 포스트 작성 루틴

이 문서는 이 저장소의 주간 포스트 자동 작성 루틴(GitHub Actions `weekly-post-draft.yml`, 또는 사용자가 직접 요청하는 추가 작성 작업)이 매번 참고하는 단일 진실 소스다. 프롬프트에 내용을 중복해서 박아넣지 말고, 이 문서를 갱신해서 다음 실행이 자동으로 최신 판단 기준을 물려받게 한다.

## 블로그 컨셉

- 이름: 결제·핀테크 엔지니어링 브리핑
- PG/간편결제/전자금융 규제·업계 동향과, PG·선불 사업 운영에 필요한 인프라·시스템 구성을 백엔드 엔지니어 관점에서 분석
- 운영자는 익명이다 — 소속·직함·실명 등 신상정보를 글 본문, 커밋 메시지, PR 본문 어디에도 절대 포함하지 않는다
- 차별화 포인트는 "양산형 AI 콘텐츠"가 아니라는 것. 반드시 검증 가능한 구체적 근거(실제 뉴스/공시, 또는 실제 서비스명·버전·설정값)를 갖춰야 한다
- 독자는 전문가가 아니다. "이 규제가 나한테 무슨 뜻이지", "이거 어떻게 대응해야 하지" 하고 막연히 검색해서 들어오는 사람이 기본 페르소나다 — 시니어 개발자만 겨냥하지 않는다. 그렇다고 유치하게 쓰라는 뜻은 아니다. 내용의 깊이·정확성은 유지하되, 배경지식을 전제하지 않고 처음 보는 사람도 따라올 수 있게 쓴다. 자세한 규칙은 "쉬운 글쓰기 규칙" 섹션 참고

## 쉬운 글쓰기 규칙 (중요 — 모든 글에 적용)

2026-09-01에 사용자가 직접 지적한 문제: 기존 글들이 "시니어 개발자 전제 + 기초 설명 생략"으로 쓰여서, 실제 독자(전문가라기보다 "이거 어떻게 해야 하지" 하고 검색해 들어온 사람)에게는 진입장벽이 너무 높았다. 앞으로는 이 규칙을 기본값으로 따른다.

- **처음 나오는 용어·조문·서비스명은 그 자리에서 짧게 풀어준다.** "전자금융감독규정 제14조의2에 따라" 대신 "전자금융감독규정(금융회사가 지켜야 하는 보안·운영 규칙을 정한 규정)의 클라우드 이용 관련 조항에 따라"처럼, 처음 보는 사람이 문장만 읽고도 뭔지 감이 오게 쓴다. 이미 이 글 안에서 한 번 풀어준 용어는 이후엔 줄여 써도 된다
- **"왜 이게 나한테 중요한지"를 각 섹션 첫 문장에 놓는다.** 조문 요약부터 시작하지 않고, "이거 안 하면 어떤 일이 생기는지"부터 말한 다음 세부 내용으로 들어간다
- **문장은 짧게, 하나의 문장에 하나의 생각만.** 여러 조건과 예외를 한 문장에 욱여넣지 않는다
- **숫자·기준은 비교 대상을 붙여서 감을 준다.** "RTO 3시간"이라고만 하지 않고 "장애가 나면 3시간 안에 복구해야 한다는 뜻"까지 붙인다
- **정확성은 절대 희생하지 않는다.** 쉽게 쓰는 것과 틀리게 쓰는 것은 다르다 — 단순화하다가 규정 내용이 왜곡되면 안 된다. 어려운 개념을 없애는 게 아니라, 그 개념까지 가는 계단을 하나씩 만들어주는 것이다
- **체크리스트·참고자료는 그대로 실무형으로 유지한다.** 쉬운 글쓰기는 설명 방식에 적용하는 규칙이고, 체크리스트 항목 자체를 유치하게 바꾸라는 뜻이 아니다
- 어린아이에게 말하듯 반말·과장된 비유를 쓰라는 뜻이 아니다("~하는 거예요~" 같은 말투 금지). 성인 대상의 명료한 설명체를 유지한다

## 콘텐츠 트랙

- **트랙 A(규제·정책, 우선순위 높음)**: 그 주 실제 뉴스/공시 기반. 신뢰 출처 — 금융위원회(fsc.go.kr), 금융감독원, 법제처/국가법령정보센터(moleg.go.kr, law.go.kr), 전자신문, 머니투데이, 로펌 뉴스레터(김앤장, 율촌 등), KDI 경제정보센터
- **트랙 B(인프라·시스템, 트랙 A에 마땅한 소재가 없는 주)**: AWS/클라우드 인프라 설계, 전자금융감독규정상 클라우드 이용 신고 등 컴플라이언스, PG/선불 사업에 필요한 시스템 구성, 오픈소스·상용 툴 비교. 신뢰 출처 — AWS 공식 문서/블로그(docs.aws.amazon.com, aws.amazon.com/blogs), 오픈소스 프로젝트 공식 저장소/릴리스노트, 전자금융감독규정 원문, 금융보안원(fsec.or.kr) 가이드

트랙 B 글도 일반론으로 채우면 안 된다 — 실제 조문 번호, 실제 AWS 서비스명·설정, 실제 오픈소스 프로젝트명·버전까지 구체적으로 검증한다.

## 실행 순서

1. `content/posts/`의 기존 파일명·frontmatter를 확인해 이미 다룬 주제를 파악한다 (중복 방지)
2. `README.md`의 "콘텐츠 캘린더", "SEO 키워드 전략" 섹션을 읽는다
3. 소재 선택 순서: ① 트랙 A 리서치를 먼저 시도한다 — 구체적이고 시의성 있는 소재(특히 시행일 임박, 최근 개정)가 있으면 그것으로 진행. ② 없으면 README "전자금융업 등록 시리즈"에서 아직 안 쓴 편을 하나 고른다. 이 시리즈는 뉴스 기반이 아니라 "등록 어떻게 하는지" 검색해 들어오는 사람을 위한 평가 참고형 콘텐츠이고, **한 실행에서 한 편만** 쓴다 — 여러 편을 몰아 쓰지 않는다. ③ 시리즈도 이미 다 썼거나 이번 주 소재로 안 맞으면 트랙 B로 넘어간다
4. WebSearch/WebFetch로 1차 출처(법령 원문, 보도자료 원문, 공식 문서)까지 확인한다 — 2차 가공 기사 하나만으로 근거를 삼지 않는다
5. `content/posts/2026-09-01-pg-settlement-fund-segregation.md`의 구조를 따라 작성한다: 배경 / (트랙 A: 핵심 변경 내용, 트랙 B: 아키텍처 옵션 비교·트레이드오프) / 실무 체크리스트 / "참고자료". 단, 문장 톤은 "쉬운 글쓰기 규칙"을 따른다 — 구조는 유지하되 설명 방식은 처음 보는 사람 기준으로 쓴다

## Frontmatter 규격

```yaml
title: "..."
description: "..."
date: "YYYY-MM-DD"
tags: ["...", "...", "...", "..."]
keywords: ["...", "...", "...", "...", "..."]
category: "regulation" # 트랙 A면 "regulation", 트랙 B면 "infra", 등록 시리즈면 "guide"
```

`category`는 홈페이지 카테고리 필터(`components/PostList.tsx`, 값 정의는 `lib/categories.ts`)가 그대로 쓰는 값이다. 트랙과 반드시 일치시킨다 — 잘못된 값을 넣거나 비워두면 필터에서 엉뚱한 탭에 잡히거나 아예 안 잡힌다. 등록 시리즈는 규제 뉴스(트랙 A)와 검색 의도가 달라서(시의성 뉴스 vs 언제 봐도 되는 참고 가이드) 2026-09-01부터 별도 카테고리 `guide`로 분리했다.

`keywords`는 README "SEO 키워드 전략" 목록과 연계해서 채운다. 새로운 롱테일 키워드를 발견하면 README에도 추가한다.

## 날짜 지정 규칙 (재발 이슈 — 반드시 지킬 것)

`lib/posts.ts`는 `date` 필드 내림차순으로 정렬하는데, 날짜가 같으면 정렬 순서가 파일시스템 `readdir` 순서에 의존해 보장되지 않는다.

- 한 번의 실행에서 글을 **하나만** 낼 때는 실제 오늘 날짜를 쓰면 된다 (정상 케이스, 충돌 없음)
- 여러 편을 한 번에 등록할 때는(백필, 배치 작성 등) 서로 다른 날짜를 부여해서 항상 "가장 최근에 다룬 주제가 목록 최상단"이라는 사용자 기대를 지킨다. 미래 날짜를 붙여 "예약 발행"처럼 보이게 하지 말고, 과거 빈 주차를 채우는 방식으로 날짜를 분산한다

## 발행 규칙

- **main에 직접 커밋/푸시하지 않는다.** 항상 새 브랜치 → PR. 자동화 워크플로우는 PR을 여는 것까지만 하고 멈춘다 — 머지는 사람이 한다
- PR 제목/본문에도 신상정보를 넣지 않는다
- 빌드 검증(`npm run build`) 없이 PR을 열지 않는다. 검증 후 `next-env.d.ts`, `package-lock.json` 같은 `npm install`/`build`의 부수 변경은 커밋에서 제외한다

## SEO 진화 규칙

콘텐츠 신선도만으로는 구글 노출이 늘지 않는다. 매 실행마다(또는 콘텐츠 작업이 없는 주라도 요청받으면) 아래를 함께 점검하고, 부족하면 코드/문서를 고친다.

- **내부 링크**: 새 글 본문에 관련 기존 글을 최소 1개 이상 링크한다 (`/posts/<slug>` 형태). 관련 글이 없으면 스킵 가능하지만, 있는데 안 걸면 감점 요인이다.
- **메타 설명 길이**: frontmatter `description`은 120~160자 권장(구글 스니펫이 잘리지 않는 범위). 새 글 작성 시 확인한다.
- **구조화 데이터**: `app/posts/[slug]/page.tsx`가 BlogPosting JSON-LD를 렌더링한다 (2026-09-01 추가). 페이지 구조를 바꿀 때 이 태그가 깨지지 않는지 확인한다.
- **canonical/OG/Twitter 메타**: `app/layout.tsx`, `app/posts/[slug]/page.tsx`에 canonical·OpenGraph·Twitter Card가 설정돼 있다 (2026-09-01 추가). 새 메타데이터 필드를 추가할 때 이 기준을 유지한다.
- **키워드 전략 갱신**: 이번 글에서 새로 검증한 롱테일 키워드가 있으면 README "SEO 키워드 전략"에 추가한다. 검색량을 직접 확인할 수단이 없으므로, 실무자가 실제로 검색할 법한 구체적 문구(제품명·법조문번호·에러코드 등)를 우선한다 — 뭉뚱그린 키워드는 추가하지 않는다.
- **og:image 부재**: 현재 사이트는 OG 이미지가 없다(공유 시 미리보기 이미지 안 뜸). 우선순위 낮은 개선 과제로 남겨둔다 — 여력이 되면 `app/opengraph-image.tsx` 같은 동적 OG 이미지 생성을 검토한다.

## 이 문서 갱신 규칙 (자기 진화)

이 스킬을 따르기만 하지 말고, 실행 중 발견한 새로운 판단 기준·재발 방지 규칙·유용한 출처가 있으면 이 문서에 함께 반영해서 같은 커밋/PR에 포함시킨다:

- 실수를 발견해 고쳤다면 "운영 중 발견한 이슈" 섹션에 원인과 해결책을 한두 줄로 추가한다
- 새로운 신뢰 출처를 찾았다면 "신뢰 출처 목록"에 추가한다
- 트랙 선택, 날짜 지정, 구조 등 반복되는 판단에 대해 더 나은 규칙을 찾았으면 해당 섹션을 직접 고친다 (이력에만 남기고 규칙 본문은 안 고치면 다음 실행이 못 물려받는다)

이 문서는 코드와 함께 커밋되는 살아있는 매뉴얼이다. 매 실행이 다음 실행을 위한 지식을 남겨야 한다.
